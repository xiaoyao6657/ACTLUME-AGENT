# Actlume persisted data schema and migration policy

This file is the migration contract for the second-round work. A field being optional in TypeScript does not make an unknown schema version compatible.

| Store | Current version | Read behavior | Migration rule |
| --- | --- | --- | --- |
| Pi task-domain entries (`actlume.task-state.v1`) | event / projection schema 1 | Reducer accepts only version 1 and validates identity, workspace, payload and event kind. Malformed or foreign-workspace rows are excluded with a recovery issue; state is never reconstructed as success from them. | Add a new custom entry type for incompatible event semantics. Keep v1 immutable. Projection changes are derived and can be rebuilt from the Pi branch. |
| Runtime event JSONL | event schema 1 | The reader validates JSONL shape and schema version and reports the file/line on malformed or unsupported data. It does not reinterpret unknown versions as v1. Preserve the source file for diagnosis; callers must surface the read failure as incomplete/unknown evidence. | Additive optional fields stay v1. A changed event meaning or required field gets a new version and an explicit projection adapter. |
| Verification records | record schema 1 historical / schema 2 current | Schema 1 is retained for history but cannot independently establish current `checks_passed` evidence. Schema 2 requires an explicit recognized check, outcome, workspace/run identity, and current fingerprints; missing result/fingerprint stays unknown or stale. | Keep original rows. An importer may display old records as history, but must not promote them to current passing evidence. |
| Memory markdown | schema 1 legacy / schema 2 prior typed / schema 3 current | Schema 1 is read as legacy; absent trust metadata becomes `needs_review`. Schema 2 typed entries without the required identity for their scope are also excluded from recall and need review. Schema 3 carries scope identity, lifecycle, evidence and supersession metadata. Unknown versions remain visible for diagnosis but cannot become active recall. | Explicit, idempotent rewrite only. Preserve original content and source; unresolved scope or identity is not guessed. User-scope activation requires explicit current-OS-user consent; revocation disables cross-workspace recall without deleting the record. |
| Eval JSONL | run record schema 1 historical / schema 2 pairing-aware; report schema 1 | Parser accepts supported record versions and rejects malformed rows with a line number. Schema 1 records can contribute descriptive summaries but cannot qualify for strict paired comparisons. Schema 2 requires known matching control fields; unknown model revision/environment/control values exclude the pair rather than being filled with assumed constants. | Preserve historical rows. New required controls require a new record schema and explicit parser support. Never backfill experimental controls with assumed constants. |
| Policy configuration (`.actlume/policies.json`) | schema 1 | Only known rule IDs and versions are accepted. Missing files use the versioned defaults; invalid/unknown rules fail configuration loading rather than silently changing policy behavior. | Add a parser/migration adapter for incompatible config shapes. Keep security permissions and verification evidence outside optional efficiency/task-strategy toggles. |
| Check configuration (`.actlume/checks.json`) | schema 1 | Check specs are validated for command, cwd, kind, unique ID and workspace-bounded paths before they can support evidence. Missing check configuration means no required checks are configured; it does not mean checks passed. | Incompatible check semantics require a new schema version and explicit migration; do not infer check scope from a free-form command. |
| Workflow snapshots inside task entries | snapshot schema 1 | Bounded snapshot is restored only after validation; invalid checkpoint yields a recovery warning while the latest preceding valid task state remains usable. | Additive optional fields may stay v1; incompatible state shape uses a new snapshot version and a migration adapter. |

Migration invariants:

- A migration never changes a historical unknown result into a pass, accepted verdict, active memory or verified claim.
- Unsupported data is retained and surfaced as unknown/needs-review; it is not rewritten or discarded as a side effect of reading.
- Writers emit only the current schema. Migration runs are explicit, idempotent and separately testable.
- Each persisted record carries the narrowest available workspace/session/task/run/branch identity. Missing identity is a scope mismatch, not a wildcard.
- JSONL event and task projections are rebuildable. An unsupported entry may reduce completeness, but cannot erase later valid rows or be treated as a terminal successful event.
